# 🆕 v4.3 핵심 변경 요약

- 스트릭 보호권의 사용자 노출 명칭을 **불꽃 방패**로 정한다. 아이콘은 방패 안에 작은 불꽃을 넣고, 방패는 파랑/청록, 불꽃은 주황/노랑 계열로 표현한다.
- 보호권은 기존처럼 KST 자정 스케줄러에서 자동 소모한다. 보호권이 사용되면 스트릭은 유지하고 다음 앱 진입 또는 홈/스트릭 화면에서 “불꽃 방패가 어제의 스트릭을 지켜줬어요” 안내를 보여준다.
- 보호권이 없을 때는 하루 결석 즉시 0으로 초기화하지 않고 `RECOVERABLE` 상태로 전환한다. 복구 마감일은 다음 KST 하루이며, 그날 일반 학습 세트 1개를 통과하면 기존 스트릭을 이어간다.
- `RECOVERABLE` 상태에서도 다음 마감 자정까지 학습하지 않으면 `BROKEN` 처리하고 `continuousDays = 0`으로 초기화한다.
- 스트릭 캘린더는 완료일, 불꽃 방패 보호일, 복구 가능일, 실패 확정일을 구분해서 표시한다.

# 🆕 v4.2 핵심 변경 요약

- 부모 커스텀 퀘스트를 추가한다. 부모가 실세계 미션과 실물 약속을 만들고, 자녀 완료 요청 후 부모 승인 또는 24시간 자동 승인으로 마무리한다.
- 커스텀 퀘스트는 인앱 재화 보상을 지급하지 않고 `rewardText`만 저장한다.
- 커스텀 퀘스트 최대 노출 기준은 `ACTIVE + PENDING_CONFIRM` 합산 3개이며, `PENDING_CONFIRM`은 만료 스케줄러 대상에서 제외한다.
- 단원별 보상을 추가한다. 단계 완료 기준은 숫자 missionId가 아니라 `missions.stage + mission_sets.star_level = 1 + mission_set_progress.completed` 기준이다.
- 단원 완료 기본 보상은 1단계 기어 30, 2단계 기어 50, 3단계 기어 80 + `NORMAL` 기본 티켓 3장으로 확정한다.
- 단원별 보상은 `stage_completion_rewards` default row/upsert와 `is_triggered`로 중복 지급을 막는다.

# 🆕 v3.7 핵심 변경 요약

- `setId`를 고정 10문항 세트 ID가 아니라 진행도/API 호환용 학습 단위로 명확히 정의한다.
- 실제 문제 선택 기준은 `question_bank.set_id`가 아니라 `missionId + difficulty` 후보 풀이며, 별 난이도 비율에 따라 10문항을 런타임 구성한다.
- 선택된 10문항은 `quiz_attempts.question_ids_json`에 저장하고, check/submit/report는 이 attempt 문항 목록을 기준으로 검증한다.
- 외부 API 응답의 `score`는 100점 환산 점수로 통일하고, 정답 개수는 `correctCount`로 표현한다.
- submit/report의 `rewards`는 `{ gear, exp, fragments }` 객체 구조를 정본으로 둔다.

# 🆕 v3.5 핵심 변경 요약

- 기존 퀴즈 하트는 세션 내부 목숨 UI로 유지하되, 하트가 0이 된 경우 사용자가 재화를 써서 1회 부활하거나 문제 세트를 포기하고 홈으로 돌아가는 플로우를 정본화한다.
- 새 계정 재화는 `톱니바퀴(gear)`으로 정의한다. 에너지와 분리된 소모성 재화이며, MVP 사용처는 퀴즈 하트 회복과 스트릭 보호권 구매로 제한한다.
- 하트 회복은 `POST /api/mission-attempts/{attemptId}/revive`로 처리하며, 일반 모드 attempt당 1회만 허용한다. 성공 시 톱니바퀴를 차감하고 `remainingLives`를 3으로 복구한다.
- 하트 회복을 하지 않는 경우 FE는 `POST /api/mission-attempts/{attemptId}/abandon`을 호출하고 홈으로 이동한다. 이 경우 시작 시 차감한 에너지는 환불하지 않으며, XP/보상/진행도/스트릭/퀘스트/업적은 반영하지 않는다.
- 스트릭 보호권은 **불꽃 방패**라는 사용자 노출명으로 표시한다. 기존 자동 소모 정책을 유지하되, `POST /api/streak/shields/purchase`로 톱니바퀴를 사용해 보호권을 추가 구매할 수 있다.
- 보호권이 없을 때 하루 결석하면 즉시 초기화하지 않고 `RECOVERABLE` 상태로 전환한다. 복구 마감일 안에 일반 학습 세트 1개를 통과하면 기존 스트릭을 이어가고, 마감일까지 미완료면 `continuousDays = 0`으로 확정 초기화한다.

# 🆕 v3.4 핵심 변경 요약

- `setId`는 진행도, attempt, 복습, check/submit/report 연결을 위한 학습 단위 식별자로 유지한다.
- `MissionQuestionSetFactory`는 전달받은 `setId`로 `mission_set`을 조회하고, 해당 세트의 `missionId`와 `starLevel` 정책을 기준으로 문항을 선택한다.
- 실제 문항 조회 조건은 `question_bank.set_id = setId`가 아니라 `question_bank.mission_id = missionId`와 개별 문항 `difficulty`다.
- 사용자가 세트에 진입하면 서버는 별 난이도 비율에 맞춰 10문항을 런타임 선택하고, 선택 결과를 `quiz_attempts.question_ids_json`에 저장한다.
- 문제은행 운영 풀은 총 1,056문항으로 통일한다. 96세트 x 10문항 = 960문항은 플레이 기준 규모이며, 추가 HIGH 96문항은 품질 보정/교체/운영 예비 풀로 관리한다.

# 🎯 PRD 요약

## 문제 정의

초등학생이 AI를 안전하고 비판적으로 사용하는 학습 루프를 만들고, 부모는 자녀의 학습 현황과 개인정보 위험 신호를 확인할 수 있어야 합니다. AImong의 MVP는 "퀴즈로 학습하고, 챗봇으로 연습하고, 부모가 최소한의 신뢰 신호를 확인하는 흐름"을 안정적으로 제공하는 데 집중합니다.

## 목표

- 첫 주 안에 자녀 계정의 미션 1회 이상 완료율을 높인다.
- 첫 미션 완료 사용자의 7일 내 재방문율을 높인다.
- 자녀 사용자의 챗봇 1회 이상 사용률을 높인다.
- 부모 계정의 자녀 요약 화면 조회율을 높인다.

## 비목표

- iOS 동시 출시
- 실시간 멀티플레이 또는 리그 시스템
- 서버 기반 개인정보 문맥 판별
- 오프라인 완전 지원

## 성공 지표

- 출시 2주 내 자녀 계정의 60% 이상이 첫 미션을 완료한다.
- 첫 미션 완료자의 40% 이상이 7일 내 3회 이상 재방문한다.
- 부모 계정의 50% 이상이 자녀 요약 화면을 1회 이상 조회한다.

## 오픈 질문

| 유형 | 로그인 방식 | 접근 화면 | 비고 |

### 계정 구조

```jsx
[부모 계정] ─── Google UID (Firebase)
     │
     └── [자녀 프로필] ─── 6자리 코드 (예: 482917)
              │
              ├── xp_data (totalXp·todayXp·weeklyXp·gachaPullCount)
              ├── pet_state (장착 펫 ID·pet.xp·단계)
              ├── streak (연속 학습 기록·보호권)
              ├── wallet (톱니바퀴 잔액·재화 사용 원장)
              ├── gacha_data (티켓·조각·보유 펫 목록)
              ├── mission_sets / mission_set_progress / mission_attempts / mission_daily_progress (학습 세트 정의·완료 진행도·시도 로그·일별 요약)
              ├── daily_quests (오늘 퀘스트 달성 현황)
              ├── weekly_quests (이번 주 퀘스트 달성 현황)
              └── achievements (달성한 업적 기록)
```

### 핵심 제약

- 만 14세 미만 → 부모가 Google 계정으로 먼저 가입 후 자녀 코드 발급 (개인정보보호법 제22조의2)
- 자녀 계정 저장 데이터: **닉네임 + 코드만** (실명·이메일·생년월일 수집 안 함)
- Supabase는 MVP에서 PostgreSQL 저장소로 사용한다. 앱 인증/인가의 1차 검증은 Spring Boot에서 수행한다.
- 부모 API는 Firebase ID Token 검증 후 `parent_id`를 확정한다.
- 자녀 API는 서버 발급 CHILD JWT와 `child_profiles.session_version`을 함께 검증해 코드 재발급·로그아웃·회원탈퇴 시 기존 세션을 무효화한다.
- Supabase RLS(Row Level Security)는 방어 계층으로 적용하되, 현재 앱 권한 모델은 백엔드 서비스 계층 검증을 정본으로 둔다.

### 4-2-1. 톱니바퀴 재화 정책

```
[재화 정의]
톱니바퀴(gear) = 계정 단위 소모성 재화
에너지(energy) = 새 일반 학습 세트 시작권
퀴즈 하트(lives) = 한 attempt 안에서만 쓰는 목숨 UI

[사용처]
1. 퀴즈 하트 회복
   - 하트가 0이 된 attempt에서만 사용 가능
   - 일반 모드 attempt당 최대 1회
   - 비용: HEART_REVIVE_COST = 10 톱니바퀴
   - 성공 시 remainingLives = 3, reviveCount += 1
   - 복습 모드는 기본적으로 재화 부활을 제공하지 않는다

2. 스트릭 보호권 구매
   - 비용: STREAK_SHIELD_COST = 30 톱니바퀴
   - 성공 시 shieldCount += 1
   - 보호권은 기존처럼 자정 스케줄러에서 미션 미완료 감지 시 자동 소모된다

[획득처]
- MVP 기본 지급처는 퀘스트/업적/복귀 보상/운영 보상 중 일부로 제한한다.
- 미션 submit 실패, check API, 에너지 추가, 하트 회복 자체는 톱니바퀴를 지급하지 않는다.

[원장]
- 모든 증감은 currency_transactions에 기록한다.
- reason은 HEART_REVIVE, STREAK_SHIELD_PURCHASE, QUEST_REWARD, ACHIEVEMENT_REWARD, RETURN_REWARD, ADMIN_ADJUST 중 하나를 사용한다.
```

### 4-3-1. 하트와 피로도 분리 정책

```
[용어 분리]
퀴즈 하트(lives) = 한 번의 퀴즈 세션 안에서만 쓰는 목숨 UI
에너지(energy) = 계정 단위로 미션 시작 가능 여부를 제어하는 자원

[퀴즈 하트]
- 퀴즈 세션 시작 시 기본 3개로 초기화한다.
- 문항별 check 결과가 오답이면 현재 세션의 하트만 1개 차감한다.
- 하트가 0이 되면 해당 세션은 즉시 실패 흐름으로 이동한다.
- 퀴즈 하트는 DB에 저장하지 않으며, 홈 화면 topStatus.energy와 동기화하지 않는다.
- 세션 종료, 재시도, 새 세트 진입 시 퀴즈 하트는 새로 초기화된다.
- 복습 모드도 별도 세션 UI 하트를 사용할 수 있으나, 에너지에는 영향을 주지 않는다.
- 하트가 0이 되면 FE는 결과를 즉시 제출하지 않고 `하트 회복` 또는 `문제 포기` 선택지를 표시한다.
- 사용자가 하트 회복을 선택하면 `POST /api/mission-attempts/{attemptId}/revive`를 호출한다.
- 사용자가 회복하지 않으면 `POST /api/mission-attempts/{attemptId}/abandon`을 호출하고 홈으로 이동한다.

[에너지]
- 에너지는 새 미션/학습 세트 시작 가능 여부를 제어하는 계정 단위 자원이다.
- 최대 에너지는 20이다.
- 일반 모드 학습 세트 1회 시작 시 에너지 5를 즉시 차감한다.
- 에너지는 10분마다 1씩 자연 회복하며, 최대치 20을 초과하지 않는다.
- 복습 모드는 에너지를 차감하지 않는다.
- 문항 오답은 퀴즈 하트만 차감하며 에너지를 차감하지 않는다.
- 에너지가 5 미만이면 새 일반 모드 학습 세트를 시작할 수 없다.
- 에너지 차감은 문제 세트 조회와 quizAttempt 생성이 성공하는 같은 트랜잭션에서 처리한다.
- 문제 세트 준비 실패, 잠금, 인증 실패 등으로 quizAttempt가 생성되지 않으면 에너지를 차감하지 않는다.
- 이미 완료한 세트를 복습으로 시작하는 경우 에너지 제한을 적용하지 않는다.
- 에너지 추가 버튼/API는 기본 사용자 기능으로 제공한다.
- 에너지 추가는 `child_profiles.energy`를 최대치 이하로 증가시키는 충전 기능이며, 학습 완료나 보상 이벤트로 간주하지 않는다.
```

## 8-new. FEATURE 08 — 부모 커스텀 퀘스트

### 담당: BE (문한일) — API·DB·스케줄러·FCM | FE (임다빈) — 부모 UI·자녀 카드 UI

### 기능 개요

부모가 앱 외부의 실세계 행동을 퀘스트로 만들어 자녀에게 부여하는 기능이다. 커스텀 퀘스트는 앱이 자동 검증할 수 없는 미션을 부모-자녀 간 약속 형태로 운영한다.

### 상태 흐름

```
[부모] 퀘스트 생성
  └─ ACTIVE
      └─ 자녀 홈/퀘스트 팝업 부모님 탭에 노출
          └─ [자녀] 완료 요청
              └─ PENDING_CONFIRM
                  ├─ [부모] 승인 → COMPLETED
                  └─ 24시간 경과 → AUTO_CONFIRMED

만료 시각 도달
  ├─ ACTIVE → EXPIRED
  └─ PENDING_CONFIRM → 만료 처리하지 않음
```

### 핵심 정책

- 실물 약속 텍스트(`rewardText`)만 저장하고, `rewardType`/`rewardAmount` 같은 인앱 보상 컬럼은 두지 않는다.
- 자녀에게 표시되는 퀘스트는 `ACTIVE + PENDING_CONFIRM` 합산 최대 3개다.
- 취소는 `ACTIVE` 상태에서만 허용한다.
- 자녀가 기한 내 완료 요청을 눌러 `PENDING_CONFIRM`이 된 퀘스트는 만료시키지 않고 부모 승인 또는 자동 승인으로 마무리한다.
- 자동 승인은 `completed_at <= now() - interval '24 hours'` 기준으로 처리한다.
- 퀘스트 관련 FCM은 `questRewardEnabled` 설정과 부모 5회/일 총량 정책에 포함한다.

### API 요약

```

GET    /api/parent/children/{childId}/custom-quests
PATCH  /api/parent/custom-quests/{questId}/confirm
DELETE /api/parent/custom-quests/{questId}
GET    /api/child/custom-quests
POST   /api/child/custom-quests/{questId}/complete
```

## 9-new. FEATURE 09 — 단원별 보상

### 담당: BE (문한일) — 트리거 로직·DB·재화 원장·FCM | FE (임다빈) — 완료 축하 팝업·부모 대시보드 단계 탭

부모가 각 학습 단계 완료 시 보여줄 실물 약속 보상을 미리 설정할 수 있다. 부모가 설정하지 않아도 시스템 기본 기어 보상은 자동 지급된다.

### 완료 기준

```
1단계 완료: missions.stage = 1인 모든 활성 미션의 starLevel 1 세트 완료
2단계 완료: missions.stage = 2인 모든 활성 미션의 starLevel 1 세트 완료
3단계 완료: missions.stage = 3인 모든 활성 미션의 starLevel 1 세트 완료
```

완료 판단은 `mission_set_progress.completed = true`, `mission_sets.star_level = 1`, `mission_attempts.is_review = false`, `mission_attempts.is_passed = true` 기준이다. 리뷰 모드와 실패 제출은 단계 완료 보상 트리거에 포함하지 않는다.

### 기본 보상

```jsx
STAGE_DEFAULT_GEAR_REWARD = { 1: 30, 2: 50, 3: 80 }
STAGE_DEFAULT_TICKET_REWARD = { 1: 0, 2: 0, 3: 3 } // NORMAL 기본 티켓
```

### 중복 지급 방지

- `stage_completion_rewards`는 `UNIQUE(child_id, stage_number)`를 가진다.
- 자녀 생성 시 1~3단계 row를 `reward_text = null`로 생성하거나, 조회/수정/트리거 시 upsert한다.
- 지급 시 `SELECT ... FOR UPDATE`로 row를 잠그고 `is_triggered = false`일 때만 지급한다.
- 지급 후 `is_triggered = true`, `triggered_at = now()`로 저장한다.

### 9-2. 가챠 실행 API

```jsx

  Body: { childId, ticketType: "NORMAL" }

1. 티켓 보유 확인 → 없으면 400 에러
2. 트랜잭션 시작
3. 티켓 1장 차감 (tickets 테이블 update)
4. child.gachaPullCount += 1  // 누적 뽑기 횟수 증가
5. gachaPullCount로 확률 구간 계산
   - 0~19:  Lv.1 / 20~49: Lv.2 / 50~99: Lv.3 / 100+: Lv.4

   // NORMAL 티켓: 유일한 기본 티켓. 기본 확률표 그대로 사용

   // 확률 상승 규칙 (섹션 9-4 참고)
   srBonus = Math.floor(srMissCount / 10) * 10  // 10번 단위 +10%씩
   영웅+ 확률 = min(기본영웅+ + srBonus, 100)   // 100% 초과 방지
   일반 확률  = max(0, 기본일반 - srBonus)       // 음수 방지
   // 일반이 0%가 된 경우: 남은 등급 비율대로 재정규화

7. 확률 보정 적용 후 가중 랜덤으로 등급 결정
8. 가중 랜덤으로 등급 결정 → 해당 등급 내에서 균등 랜덤으로 캐릭터 결정
9. 구간 레벨업 체크 (이전 횟수 구간 != 현재 구간)
   → 레벨업이면: tickets.normal += 2, shieldCount += 1
10. 중복 여부 확인 → 중복이면 조각으로 변환
    → 신규이면: pets 테이블에 {petId, childId, xp: 0, stage: EGG} 추가
11. 결과 DB 저장
12. 트랜잭션 커밋
13. 결과 반환

Response:
{
  "result": {
    "petId": "pet_rare_003",
    "petName": "번개몽",
    "grade": "RARE",
    "isNew": false,
    "fragments": 3         // 중복이면 조각 수, 신규면 0
  },
  "srMissCount": 8,         // 현재 영웅 이상 미획득 연속 횟수 (10 이상이면 FE에 확률업 표시)
  "srBonus": 0,             // 현재 적용 중인 영웅+ 확률 보너스 (srMissCount/10*10)
  "remainingTickets": 2
}
```

### 9-4. 확률 상승 시스템 (구 천장 방식 대체)

```jsx
// ⚠️ 기존 소프트/하드 천장 완전 제거
// → 10번 단위 누적 상승 + 영웅 이상 뽑히면 즉시 리셋으로 대체

[확률 상승 규칙]
  srBonusRaw = srMissCount >= 10 ? (srMissCount - 9) * 1% : 0%
  srBonus = min(srBonusRaw, 현재 NORMAL 기본 확률)
  // srMissCount 0~9:   srBonus = 0%   (기본 확률 그대로)
  // srMissCount 10:    srBonus = 1%
  // srMissCount 11:    srBonus = 2%
  // srMissCount 20:    srBonus = 11%  ... 1회 단위 누적

  영웅 확률 = 기본영웅 + srBonus               // 현재 구현은 EPIC 확률에 applied srBonus를 더함
  일반 확률 = 기본일반 - srBonus               // srBonus는 기본일반 확률을 초과하지 않음
  // srBonus는 API 응답의 실제 적용치(appliedSrBonus) 기준으로 반환
  // NORMAL 티켓이 아닌 경우 srBonus는 0.0으로 반환

[리셋 조건]
  영웅 이상 획득 시 → srMissCount = 0 즉시 리셋
  // 하드 천장(50번 보장) 없음 — srBonus 무한 누적으로 대체

[예시]
  srMissCount = 10: srBonus = 1% → Lv.1 기준 영웅 확률 3.5% → 4.5%
  srMissCount = 20: srBonus = 11% → Lv.1 기준 영웅 확률 3.5% → 14.5%
  영웅 뽑힘!  → srMissCount = 0, 다음 뽑기부터 기본 확률

[FE 표시]
  srMissCount >= 10 일 때만 표시:
  "💜 영웅 확률 +{srBonus}% 업 중! ({srMissCount}번째 도전 중)"
  srMissCount < 10: 표시 없음
```

| EC-14 | **자녀 추가/삭제와 활성 자녀 선택 충돌** | 부모 홈 진입 시 GET /api/parent/me 또는 bootstrap의 children summary 기준으로 활성 자녀를 재선택한다. 삭제된 childId는 로컬 캐시에서 제거한다. | FE |
| EC-15 | **에너지 추가로 최대 에너지 초과 시도** | 서버에서 최신 자연 회복분을 먼저 반영한 뒤 `min(maxEnergy, currentEnergy + amount)`로 저장한다. 이미 최대치이면 값은 유지하고 성공 응답으로 현재 상태를 반환한다. | BE + FE |
